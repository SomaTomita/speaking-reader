# Word-by-word (karaoke) highlight — design

Date: 2026-06-09
Project: IELTS Speaking Reader (`reader/`)
Status: Approved (brainstorming), ready for implementation planning.

## Goal

While a lesson plays, emphasise the word currently being pronounced, in sync
with the audio, so a learner can follow and shadow word by word. Today the
reader highlights at the sentence level only.

## Decisions (locked during brainstorming)

1. **Target surface: the live reader app.** CSS/JS only. No video rendering, so
   the `css-animations` and `remotion-best-practices` skills do not apply.
2. **Highlight style: karaoke fill.** Read words = normal colour. Active word =
   accent background + white text (the fill head). Upcoming words = muted grey
   (`--text-muted`). Progress is visible at a glance and finished text stays
   readable.
3. **Timing source: real edge-tts word cues.** Regenerate audio once with
   `saveSubtitles: true` so each sentence MP3 gets a `{file}.mp3.json` sidecar of
   per-word timestamps. No estimation, no forced alignment.

## Key facts grounding the design

- Audio is per-sentence MP3, named `audio/uk/{g}_{l}_{s}_{sent}.mp3` (821 files,
  `en-GB-SoniaNeural`). Generated by `node-edge-tts` in `src/build/generate-audio.ts`.
- `node-edge-tts` v1.2.10 supports `saveSubtitles: true`. It enables
  `wordBoundaryEnabled` on the request and writes `{audioPath}.json` =
  `[{ part: string, start: number, end: number }]`, where `start`/`end` are
  media-time milliseconds. Same TTS engine as the MP3, so cues are exact.
- The MP3 playback path uses an `<audio>` element. `audio.currentTime` is
  media-time and is independent of `playbackRate`, so cues stay valid at any
  speed-slider value.
- A Web Speech API fallback exists for browsers without the MP3 set; it exposes
  native per-word `onboundary` events.

## Chosen approach: lazy per-lesson cue fetch (Approach A)

On `openLesson`, fetch that lesson's cue JSON files in parallel (a lesson has
~1–10 segments, each a few sentences, so a handful of tiny JSON fetches),
render word spans, and cache in the existing `prepared` Map.

Rejected alternatives:
- **B — bake cues into `data.js` at build.** Zero runtime fetch but grows
  `data.js` and couples `build:data` to `build:audio` ordering (cues do not exist
  on the first data build). Not worth the fragility.
- **C — estimate timing, no regen.** Rejected: accurate cues are cheaply
  available.

## Design

### 1. Build pipeline (`src/build/generate-audio.ts`)
- Add `saveSubtitles: true` to the `EdgeTTS` config.
- Change the skip condition from "skip if `.mp3` exists" to "skip only if **both**
  `.mp3` and `.mp3.json` exist," so the first run backfills cues for all 821
  sentences and later runs stay incremental.
- The audio-manifest stays as is. Cue presence is discovered by the app fetching
  the sidecar (404 → fallback).

### 2. Word spans from cues (robustness)
- Render one `<span class="word">` per cue, in cue order. Highlight index then
  equals audio cue index, so there is no fragile whitespace/punctuation
  re-alignment. Concatenated cue `part`s reproduce the sentence text (the library
  reconstructs in-between characters when writing the sidecar).
- Missing cue file → fall back to the current single sentence span with
  sentence-level highlight (no regression).

### 3. Playback sync (`src/app/speech-engine.ts`)
- On the `<audio>` path, run a `requestAnimationFrame` loop while playing:
  `t = audio.currentTime * 1000`; advance a cue pointer; on change, fire a new
  `onWord(segmentIndex, wordIndex)` callback. Stop the loop on pause/stop/ended.
- rAF (not `timeupdate`, which is ~4 Hz) for a snappy fill head.
- Web Speech fallback: drive the same `onWord` from native `onboundary`. If even
  that is unavailable, degrade to sentence-level highlight.

### 4. State machine + CSS (`public/styles.css`)
- Each word span is in one of: default (upcoming, `--text-muted`), `is-active`
  (accent bg + white), `is-read` (normal text colour).
- Transition `background-color`/`color` at the existing 180ms. `prefers-reduced-motion`
  already snaps transitions to 0s via the global rule, so it stays functional.
- Auto-scroll stays at **sentence** granularity (scroll when the sentence
  changes, not per word) to avoid jitter.
- Active-word background uses `--accent-active` (#5f6f5e, 5.35:1 with white)
  rather than `--accent` (#7b8b7a, 3.61:1) so white-on-accent passes WCAG AA.

### 5. App wiring (`src/app/reader-app.ts`)
- Extend `PreparedSegment` (or a parallel structure) to hold per-sentence cue
  arrays loaded lazily.
- `renderSegments` builds word spans from cues when present, else the current
  sentence span.
- New `onWord` handler sets `is-read`/`is-active` classes and triggers
  sentence-level scroll on sentence change.

### 6. Accessibility
- Word spans are non-interactive; screen-reader reading order is unchanged.
- The ARIA live region keeps announcing play/pause/stop only, not per word.

## Files touched
- `src/build/generate-audio.ts` (cue generation)
- `src/app/speech-engine.ts` (rAF sync, `onWord` callback, fallback)
- `src/app/reader-app.ts` (lazy cue fetch, word-span render, highlight handler)
- `public/styles.css` (karaoke states)
- No new dependencies.

## Testing
- Unit: cue→span alignment (concatenated `part`s equal the sentence text) and
  the pointer-advance logic against a sample cue array (pure functions, no audio).
- Manual: verify sync on one Part 1 lesson and one Part 2 lesson, at 1.0x and a
  non-1.0x speed, plus the Web Speech fallback path.

## Out of scope
- Video / Remotion output.
- Per-word click-to-seek.
- Changing the existing sentence-level pause behaviour.
